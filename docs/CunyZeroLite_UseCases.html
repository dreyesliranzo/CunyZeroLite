UC-01
User LoginIMPLEMENTED

Actors

Student, Instructor, Registrar

Preconditions

User has a registered account in the system.

Postconditions

Session token stored; user redirected to /dashboard with role-appropriate view.

Diagram Type

Petri Net

▶ Normal Scenario

  1. User navigates to /login.
  2. System renders email/password form.
  3. User enters credentials and clicks "Sign In."
  4. System calls loginUser(email, password) via Server Action.
  5. DB returns matching User record.
  6. System stores role and firstName in session/cookie.
  7. If mustChangePassword === true, system redirects to /change-password; otherwise redirects to /dashboard after 1.5 s.

▶ Exceptional Scenarios

  1. Invalid credentials: DB returns no match → system shows "Invalid credentials." error; form reset.
  2. Suspended account: user.suspended === true → system shows suspension notice; login blocked.
  3. Terminated account: user.terminated === true → system shows termination notice; login blocked.
  4. DB unavailable: Prisma throws → Server Action returns { success: false, error: "Server error." }.

UC-02
Course EnrollmentIMPLEMENTED

Actors

Student

Preconditions

Student logged in; semester period is REGISTRATION; student not suspended/terminated.

Postconditions

Enrollment record created with status ENROLLED; seat count decremented.

Diagram Type

Petri Net

▶ Normal Scenario

  1. Student selects a course and clicks Enroll.
  2. System POSTs to /api/enroll with courseId.
  3. API checks eligibility: student not suspended, semester is REGISTRATION.
  4. API checks seat availability: current enrollment count < course.maxStudents.
  5. DB creates Enrollment { status: "ENROLLED" }.
  6. System returns 201; UI shows success confirmation.

▶ Exceptional Scenarios

  1. Already enrolled: Unique constraint on (userId, courseId) violated → 409 Conflict.
  2. Course full: Seat check fails → system auto-prompts to join waitlist.
  3. Not REGISTRATION period: Semester period ≠ REGISTRATION → 403 Forbidden.
  4. Student suspended: user.suspended === true → 403; enrollment blocked.
  5. Course cancelled: course.cancelled === true → 400 Bad Request.

UC-03
Submit Graduation RequestIMPLEMENTED

Actors

Student, Registrar

Preconditions

Student logged in; no prior pending GraduationRequest; no outstanding fineOwed.

Postconditions

GraduationRequest created; Registrar reviews; User.graduated set to true on approval.

Diagram Type

Petri Net

▶ Normal Scenario

  1. Student submits graduation request from Student Tools.
  2. API verifies no outstanding fines and GPA ≥ 2.0.
  3. DB creates GraduationRequest { status: "PENDING" }.
  4. Registrar reviews request in admin panel.
  5. Registrar checks: all required courses completed, GPA ≥ 2.0, no holds.
  6. Registrar approves → DB sets request.status = "APPROVED", user.graduated = true.

▶ Exceptional Scenarios

  1. GPA below minimum: GPA < 2.0 → request denied with reason.
  2. Outstanding fines: user.fineOwed > 0 → 400; student must clear balance first.
  3. Duplicate request: PENDING request already exists → 409 Conflict.
  4. Registrar denies: Missing requirements → status set to DENIED with reason.

UC-04
Join WaitlistIMPLEMENTED

Actors

Student

Preconditions

Student logged in; course is full; student not already on waitlist or enrolled.

Postconditions

Waitlist record created with next sequential position.

Diagram Type

Sequence Diagram

▶ Normal Scenario

  1. Student clicks "Join Waitlist" on a full course.
  2. Portal sends POST /api/enroll with courseId and waitlist flag.
  3. API queries waitlist.count({ where: { courseId } }) to get next position (n+1).
  4. API checks no existing record for (userId, courseId).
  5. DB creates Waitlist { position: n+1, status: "WAITING" }.
  6. API returns 201 with position number.
  7. Portal shows "You are #n on the waitlist."

▶ Exceptional Scenarios

  1. Already on waitlist: Unique constraint on (userId, courseId) → 409 Conflict; "Already on waitlist."
  2. Already enrolled: Enrollment record exists → 409; cannot waitlist for an enrolled course.
  3. Course not full: Seat became available between UI render and submission → enroll directly instead.

UC-05
View Grades & TranscriptIMPLEMENTED

Actors

Student

Preconditions

Student authenticated; enrollment records exist with grade values (after GRADING period).

Postconditions

Student views grades per course with GPA summary.

Diagram Type

Sequence Diagram

▶ Normal Scenario

  1. Student navigates to /grades_transcript from dashboard.
  2. Next.js Server checks session; retrieves userId.
  3. Server queries enrollment.findMany({ where: { userId }, include: { course: true } }).
  4. DB returns all enrollment records with course details and grade values.
  5. Server computes cumulative GPA from grade values.
  6. Page renders grade table with per-course grades, credits, and overall GPA.

▶ Exceptional Scenarios

  1. No session: Auth check fails → redirect to /login (302).
  2. No enrollments: findMany returns empty array → display "No grade records found."
  3. Grades not yet released: Semester still ONGOING/REGISTRATION → enrollment.grade is null; display "Pending."
  4. DB timeout: Prisma throws → 500 error page.

UC-06
AI Chat (Lite Assistant)IMPLEMENTED

Actors

Visitor (home page), Student (portal)

Preconditions

OpenAI API key set in environment. Chat widget open.

Postconditions

AI response displayed in chat bubble; conversation history maintained client-side.

Diagram Type

Sequence Diagram

▶ Normal Scenario

  1. User types a message and presses Send or Enter.
  2. HomeChatWidget appends user message to local state; sends POST /api/chat { message, chatType }.
  3. API calls getAIResponse(message, chatType) in src/lib/ai.ts.
  4. ai.ts runs searchPolicies(message): keyword scores policy.json; returns top-4 matched policies.
  5. ai.ts constructs system prompt injecting policy context and chat type (home vs portal).
  6. OpenAI API (gpt-4o-mini, max 500 tokens) returns completion.
  7. API returns { reply }; widget appends assistant message bubble.

▶ Exceptional Scenarios

  1. OpenAI error: API throws (rate limit, network) → 500; widget shows "Sorry, I couldn't generate a response."
  2. No policy match: Score = 0 for all policies → fallback context injected: "Use general knowledge…"
  3. Empty input: Client-side guard prevents sending empty or whitespace-only messages.

Student (filer), Instructor or Student (target), Registrar (resolver)

Preconditions

Filer logged in; target user exists; complaint must not be self-filed.

Postconditions

Complaint record PENDING; Registrar notified; resolved to RESOLVED or DISMISSED.

Diagram Type

Sequence Diagram

▶ Normal Scenario

  1. Student fills complaint form with target userId and description.
  2. API verifies filerId !== targetId.
  3. API verifies target user exists in DB.
  4. DB creates Complaint { status: "PENDING" }.
  5. Registrar reviews complaint list in admin panel.
  6. Registrar PATCHes complaint → status: "RESOLVED", resolution: text.

▶ Exceptional Scenarios

  1. Self-complaint: filerId === targetId → 400 "Cannot file a complaint against yourself."
  2. Target not found: DB returns null for target → 404 "User not found."
  3. Empty description: Validation error → 422 Unprocessable Entity.

Registrar

Preconditions

Registrar authenticated; target student exists; student not already terminated.

Postconditions

Sequence Diagram

▶ Normal Scenario

  1. Registrar selects a student and issues a warning with reason.

  1. Student already terminated: user.terminated === true → 400 "Cannot warn a terminated student."

  3. Threshold triggers suspension: warnings reaches 3 → auto-suspend; student notified on next login.

Honor Roll Recognition & Warning RemovalPLANNED
⚠ Planned — HonorRoll model (type, usedToRemoveWarning, semesterId) exists. Policy: Dean's List ≥ 3.5 GPA, President's List ≥ 3.8 GPA. Honor roll status can remove one warning. No route yet.

Actors

Registrar (awards honor roll), Student (requests warning removal)

Preconditions

Semester COMPLETED; student GPA meets threshold; student has at least one active warning (for removal sub-case).

Postconditions

HonorRoll record created. Optionally: one Warning.removed = true; User.warnings decremented.

Diagram Type

Sequence Diagram

▶ Normal Scenario — Award Honor Roll

  1. Registrar triggers end-of-semester honor roll computation.
  2. System queries all students with semester GPA ≥ 3.5.
  3. System creates HonorRoll { type: "DEANS_LIST" or "PRESIDENTS_LIST", usedToRemoveWarning: false } per qualifying student.
  4. Student sees honor roll status on dashboard/profile.

▶ Normal Scenario — Use Honor Roll to Remove Warning

  1. Student requests to use their honor roll status to remove a warning.
  2. API verifies honorRoll.usedToRemoveWarning === false and student has active Warning.
  3. DB sets warning.removed = true, honorRoll.usedToRemoveWarning = true, decrements user.warnings.

▶ Exceptional Scenarios

  1. GPA below threshold: semester GPA < 3.5 → not placed on honor roll.
  2. Honor roll already used: usedToRemoveWarning === true → 400 "Already used to remove a warning."
  3. No active warnings: No Warning with removed=false → 400 "No warnings to remove."
  4. Duplicate honor roll: Unique constraint on (userId, semesterId, type) → 409.

UC-19
Drop / Withdraw from CoursePLANNED
⚠ Planned — Policy explicitly describes drop (first 2 weeks, no record) and withdrawal (after deadline, W grade on transcript). Enrollment.status field can support ENROLLED / DROPPED / WITHDRAWN states. No drop/withdraw route yet.

Actors

Student

Preconditions

Student enrolled in course; semester ONGOING or within drop window.

Postconditions

Drop: enrollment removed, no transcript record. Withdrawal: enrollment.status = "WITHDRAWN", grade = "W" on transcript; GPA unaffected.

Diagram Type

Sequence Diagram

▶ Normal Scenario — Drop (within first 2 weeks)

  1. Student clicks Drop Course within the drop window.
  2. API verifies current date is within drop deadline.
  3. DB deletes Enrollment record (no transcript entry).
  4. If a student was on waitlist, first waitlisted student is auto-enrolled.
  5. System returns 200; course removed from student's schedule.

▶ Normal Scenario — Withdraw (after drop deadline)

  1. Student clicks Withdraw Course after drop deadline.
  2. API verifies semester is ONGOING (not COMPLETED).
  3. DB sets enrollment.status = "WITHDRAWN" and enrollment.grade = "W".
  4. System notes W on transcript; GPA unchanged.
  5. System checks if dropping below full-time (12 credits) and warns about financial aid impact.

▶ Exceptional Scenarios

  1. Drop window closed: Date after 2-week deadline → redirect to Withdraw flow instead.
  2. Semester COMPLETED: Cannot drop or withdraw after semester ends → 400.
  3. Not enrolled: Enrollment record not found → 404.
  4. Financial aid warning: Dropping below full-time → UI shows warning before confirming.
